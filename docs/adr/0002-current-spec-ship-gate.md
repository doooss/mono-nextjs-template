# ADR-0002 — 현재 사양 중심 출고 게이트 (적대적 리뷰 필수 · 커밋 단위 기록)

- **Status**: Accepted
- **Date**: 2026-11-21
- **Refs**: 261121_001_monorepo-bootstrap
- **Supersedes**: —

## Context

task 파일에 과정만 쌓이면 "지금 시스템이 어떻게 동작하는가" 는 여러 task 와 코드에 흩어진다.
작업 종료를 prod 배포 확인에 묶으면 코드 완료 후에도 task 가 오래 열려 있고, 사람 확인 단계(manual)가 늘어난다.
목표는 **현재 사양과 흐름을 남기는 것** — 언제든 `docs/specs/` 만 읽으면 현재 동작을 알 수 있어야 한다.

## Decision

done 조건을 6단계 출고 게이트로 고정한다: 로컬 검증 → **적대적 리뷰(필수, 새 컨텍스트 서브에이전트)** →
작업 기록 압축(`최종 사양` · `예외 케이스` · `결정` · `검증`) → ADR(또는 `none — 사유`) →
현재 사양 덮어쓰기(`docs/specs/` 개체 단위, FE page 는 스크린샷 + 사용 설명서) → 한 커밋.
prod / sandbox 확인은 게이트에서 제외한다. CI 커밋 감사(`commit-audit.mjs`)가 done 으로 들어온 task 마다 게이트를 기계 검증한다.

## Alternatives

| 대안                                                  | 기각 이유                                                                                                                                                                                           |
| ----------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| OpenSpec 도입 (proposal → delta spec → archive merge) | 개념은 같다 (specs = 현재 진실, change = 델타). 다만 CLI · 델타 문법(ADDED/MODIFIED) 학습 비용 대비, 개체 문서를 직접 덮어쓰고 git diff 로 델타를 보는 쪽이 단순. 현재 사양 / 변경 분리 원칙만 차용 |
| GitHub Spec Kit (constitution → spec → plan → tasks)  | 기능 착수 전 문서 생성에 무게 — 구현 후 "실제 동작" 기록이 목표인 이 흐름과 반대 방향                                                                                                               |
| 리뷰를 선택 사항으로                                  | 작은 변경일수록 리뷰가 생략되고, 예외 케이스 기록이 비게 된다                                                                                                                                       |
| 사양에 변경 이력 누적                                 | 문서가 길어지고 현재 동작을 찾기 어려움. 이력은 git · task · ADR 이 이미 가진다                                                                                                                     |
| 배포 확인 후 archive                                  | 작업 종료가 배포 일정에 묶임. 배포 검증은 릴리스 파이프라인 / 모니터링 책임                                                                                                                         |

## Consequences

- **긍정**: `docs/specs/` = 현재 동작의 단일 출처. 예외 케이스가 리뷰 결과로 반드시 남는다. 커밋 하나로 코드 · 기록 · 사양 · 결정을 추적.
- **부정 / 비용**: 출고마다 리뷰 + 문서 갱신 시간. 사양이 코드와 어긋나면 사람이 고쳐야 한다 (CI 는 존재 / 형식만 검증, 내용 일치는 리뷰 공격 면 4 가 담당).
- **후속**: 엄격도는 `COMMIT_AUDIT_STRICT` 로 조절. 템플릿 seed 사양의 알려진 한계는 백로그 task 로 정리.
